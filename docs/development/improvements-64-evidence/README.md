# استعادة الوصول وسلامة التحرير — Issue #64

نفذت هذه المرحلة التحسينات الأربعة المعتمدة: استعادة الوصول، وفحص توافق المخطط عند التشغيل، وتوثيق قرارات البلاغات والجودة، ومنع ضياع التعديل المتزامن. تعتمد على سلسلة تغييرات CRUD وتوحيد القوائم السابقة حتى PR #63؛ لا تشمل تحسينات الأداء أو إعادة تصميم الواجهة العامة.

## السلوك والصلاحيات

- `/ar/forgot-password`: يسجل طلباً فعلياً للحساب النشط غير المحذوف. الرد نفسه للحساب غير المعروف، ولا تُحفظ طلبات متكررة للحساب أثناء وجود طلب مفتوح أو خلال ساعة. مسارات الاستعادة محدودة بعشرة طلبات لكل عنوان IP في نافذة المعدل الحالية، أو الحد العام إن كان أقل.
- `/ar/admin/users/recovery`: يعالج المسؤول الطلب بصلاحية `user.reset_password` القائمة، ضمن سقف السلطة نفسه المستخدم في إدارة الحسابات. إصدار الرابط يتطلب إقرار التحقق من الهوية وسبباً مكتوباً؛ الرفض مدقق أيضاً. لا تمنح هذه المرحلة صلاحيات جديدة ولا تتجاوز حماية النفس أو المساوي أو الأعلى في السلطة.
- `/ar/reset-password`: رابط عشوائي صالح لمدة 15 دقيقة ولاستخدام واحد، يعرض مرة واحدة للمسؤول ليسلمه يدوياً بعد التحقق من الهوية. لا توجد خدمة بريد أو إرسال تلقائي. يخزن الخادم بصمة الرمز فقط؛ يوضع الرمز في fragment ويزال من شريط العنوان بعد قراءته. تغيير كلمة المرور، واستهلاك الرمز، وإبطال الجلسات، والتدقيق ضمن معاملة واحدة. تغيير كلمة المرور بطريق آخر يبطل الرابط السابق.
- البلاغات والجودة: السبب يكتبه المستخدم في نافذة التأكيد ويُحفظ مع المنفذ والوقت في سجل التدقيق. تعرض الواجهة تاريخ المعالجة وروابط التشريعات المرتبطة المتاحة. يمنع الخادم القرار المتكرر أو الانتقال غير المسموح في البلاغات؛ يظهر فلتر مشكلات الجودة المحلولة والمتجاهلة.
- المراجع الثلاثة والجريدة والتنقل والصفحات والإعدادات: يرسل المحرر رقم النسخة المقروءة؛ يرفض الخادم النسخة القديمة بـ`409` قبل الكتابة، ويعيد الحقول المسموح بمراجعتها. تبقى المدخلات، ويختار المستخدم القيم الحالية أو مدخلاته لكل حقل، ثم يراجع النموذج ويعيد الحفظ. فحص الإعدادات يتم لكل الدفعة داخل معاملة، ولا يحفظ جزءاً منها عند التعارض.

## قاعدة البيانات والتشغيل

ترحيل `1700000000017-recovery-edit-revisions.ts` ينشئ `password_recovery_requests`، ويضيف `edit_revision` إلى `legislation_types` و`subjects` و`authorities` و`gazette_issues` و`platform_settings` و`navigation_items` و`public_pages`. تزيد triggers نسخة التحرير عند كل تحديث، بما فيه تغيير الحالة الإدارية من المسارات الأخرى. لا يتغير النفاذ القانوني أو المحتوى التاريخي، ولا يعاد إسناد صلاحيات.

خطوات التحديث: نسخة احتياطية → `npm run db:migrate` → `npm run db:check` → تشغيل API والعامل. لا تطبق الحماية ترحيلات تلقائياً. يشترك API والعامل في `scripts/database/schema-contract.mjs`؛ يجب تضمين هذا المجلد في إصدار النشر إلى جانب الملفات المبنية. ترفض الحماية الترحيلات المطلوبة المفقودة والأسماء غير المعروفة والحقول الأساسية المفقودة.

استثناء توافق موثق: يوجد في قاعدة التطوير ترحيل تاريخي باسم `PermissionCatalogSync1700000000011`، ومصدره محفوظ في Git بالمرجع `8496639`. كان يزامن بيانات الصلاحيات؛ يغطي الترحيل المطلوب `CanonicalRbacSecurity1700000000012` الكتالوج اللاحق. يقبل الفحص الاسم التاريخي المحدد إلى جانب جميع الترحيلات المطلوبة؛ لا يعامله بديلاً عن `ReferenceThemeDefaults1700000000011` ولا يحذف سجل الترحيل أو يتجاهل أسماء أخرى. أصلح هذا الاستثناء منع التشغيل الذي ظهر عند اختبار قاعدة التطوير القائمة.

طبق الترحيل على قاعدة التطوير بعد نسخة MariaDB كاملة بصلاحيات ملف خاصة خارج المستودع. قورنت بيانات الحسابات وكلمات المرور والأدوار والمنح بالنسخة السابقة وتطابقت. نجح `db:check` وفحص صحة API والعامل، ثم تسجيل الدخول بحساب التطوير `super` عبر المنفذ 5173 وإعادة تحميل لوحة الإدارة مع بقاء الجلسة. لم يعاد البذر أو تغيير كلمات مرور المستخدمين، ولم تُمس بيئة إنتاج.

التراجع عن الترحيل مسموح حين يكون جدول الطلبات فارغاً فقط؛ يرفض محو تاريخ استعادة محفوظ. يلزم عند وجود تاريخ الاحتفاظ بالمخطط واستخدام إصلاح لاحق أو خطة استعادة للنسخة الاحتياطية. العملاء المخصصون للـAPI يحتاجون الآن `editRevision` أو `editRevisions` عند التعديل؛ يلزم تحديث صفحة محرر كانت مفتوحة قبل ترقية التطبيق.
