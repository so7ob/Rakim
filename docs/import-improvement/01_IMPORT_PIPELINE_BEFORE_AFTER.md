# مسار الاستيراد قبل التحسين وبعده

## النطاق والبيئة الفعلية

المشروع monorepo بـnpm workspaces. الواجهة React 19 وReact Router 7 وVite 8، والخادم NestJS 12، والعامل Node.js مستقل، والوصول إلى MariaDB 10.11 عبر TypeORM `DataSource` واستعلامات SQL مباشرة. الحالة في الواجهة تدار بـReact context وhook محلي `useApi`. الاختبارات Vitest وPlaywright. بيئة التنفيذ التي نُفذت عليها المرحلة تستخدم Node.js 20.20.0، بينما `package.json` يعلن Node.js `>=22.13.0`؛ نجحت الفحوص، لكن يلزم تشغيل الإنتاج والـCI على الإصدار المعلن.

## المسار السابق

1. ترفع `/ar/admin/imports` ملفًا إلى `POST /api/v1/imports`.
2. يتحقق `ImportsService` من الحجم والامتداد والتوقيع وSHA-256، ثم يحفظ المصدر وينشئ `IMPORT_SOURCE` في `job_queue` داخل معاملة.
3. يستخرج عامل Node النص بحسب الصيغة: قراءة مباشرة لـTXT/Markdown/CSV، وMammoth لـDOCX، و`read-excel-file` لـXLSX، وPoppler لـPDF، وTesseract العربي للصور وPDF الممسوح.
4. كانت `parseStructure` تبحث عن عناوين المواد فقط بتعبير منتظم واحد، وتحفظ `preamble + articles` في `source_imports.extraction_json`.
5. كانت المعاينة تعرض النص المستخرج بجانب المصدر، ولا تعرض نتيجة بنيوية.
6. عند إنشاء المسودة، كانت الخدمة تنشئ عقدة `CHAPTER` اصطناعية واحدة بعنوان «مواد قيد المراجعة» وتربط بها كل المواد.

## السبب الجذري

المعلومة البنيوية كانت تضيع في مرحلتين متتاليتين: المحلل لا ينتج الأبواب أو الفصول أو الأقسام أصلًا، وخدمة إنشاء المسودة لا تملك عقدًا وسيطة لتعيد بناء الشجرة، فتستبدلها بعقدة اصطناعية. لذلك لم يكن الخلل عرضًا في React ولا نقصًا منفردًا في Regex؛ كان عقد البيانات بين الاستخراج والمعاينة والحفظ محدودًا بالمواد فقط.

## المسار الجديد

1. تبقى مراحل الرفع والتحقق والتخزين والاستخراج وOCR والطابور كما هي.
2. ينتج العامل `arabic-legal-structure-v2`: ديباجة، عقد مرتبة، علاقات parent keys، مواد مرتبطة بأعمق سياق صريح، حالات ثقة، وملاحظات وملخص.
3. يحفظ التمثيل نفسه في `source_imports.extraction_json`؛ لا تعاد معالجة imports القديمة تلقائيًا.
4. يعرض API إسقاط معاينة خفيفًا من التمثيل المحفوظ نفسه، مع حذف النصوص الكاملة من عناصر الشجرة والإبقاء على مقتطف قصير.
5. تعرض الصفحة counts وملاحظات وشجرة باب/فصل/قسم/مادة قبل إنشاء المسودة.
6. يتحقق `ImportsService` من أنواع العقد وترتيب الأب قبل الابن وقانونية العلاقة، ثم ينشئ التشريع والإصدار والعقد والمواد والروابط والمسؤوليات والـaudit في معاملة واحدة.
7. عند عدم وجود بنية صريحة تحفظ المواد على root بدل إنشاء بنية مخترعة.
8. يقفل `source_imports` بـ`FOR UPDATE`. الطلب المتكرر بعد نجاح الإنشاء يعيد التشريع المرتبط نفسه، والطلبان المتزامنان لا ينشئان مسودتين.

## قرارات مهمة

- استخدم المخطط الحالي: `structure_nodes.parent_id` و`articles.structure_node_id` و`sort_key`؛ لم ينشأ جدول بنية مكرر.
- تمثيل باب/فصل/قسم في الأنواع القائمة هو `TITLE / CHAPTER / SECTION`.
- المصدر الوحيد للترتيب هو الظهور في الوثيقة، لا رقم المادة.
- بقيت نتائج الإصدار القديم مدعومة عند إنشاء مسودة، بالعقدة الاصطناعية السابقة، حفاظًا على التوافق؛ المحلل الجديد يطبق على الاستيرادات الجديدة فقط.
- لا يشمل العمل إعادة تصميم CRUD أو واجهة bulk assignment.
